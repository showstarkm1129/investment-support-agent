# AI投資判断OS 要件定義書

作成日: 2026-06-22

## 1. プロジェクト概要

本プロジェクトは、自動売買で勝つことを主目的にしない。

目的は、個人投資家の情報収集、判断、振り返りを効率化し、投資意思決定の質を上げることである。

最終的に目指すものは、以下である。

> 個人投資家のためのAI投資判断OS。  
> 必要な市場情報を毎日集め、証拠に基づいて強気・弱気・反証・織り込みを整理し、音声でもインプットできるレポートを提供する。さらに、保有中レビューと反省機構により、自分だけの投資判断ログを蓄積し、意思決定の質を継続的に改善する。自動売買は最後のおまけとして扱う。

## 2. プロジェクトの思想

### 2.1 主目的

- 個人の投資判断を最高効率化する
- 必要な情報だけを毎日届ける
- 強気材料だけでなく、弱気材料、反証、織り込みを必ず確認する
- 保有中のポジションについても、持ち続ける理由を検証する
- 判断結果と過程を保存し、あとから反省できるようにする
- 自分だけの投資判断ログを蓄積する

### 2.2 自動売買の位置づけ

自動売買は主目的ではない。

自動売買は、十分なログ、検証、ペーパートレード、安全ゲート、ポジション管理、注文管理が揃った後に検討する最後のおまけ機能とする。

### 2.3 既存製品との差別化

既存のAI自動売買、ノーコード戦略作成、シグナル配信ツールに対して、本プロジェクトが狙う優位性は以下である。

- 1銘柄または少数銘柄への深い集中
- 証拠DBを中心にした根拠管理
- 強気、弱気、反証、織り込みの分離
- 保有中レビュー
- Agentごとの思考ログ
- 週次、月次の反省機構
- 日本株、日本語情報、個人の投資スタイルへの適応

既存製品が得意な領域は以下である。

- すぐ使えるUI
- ブローカー連携
- バックテスト
- 自動発注
- チャート、アラート、シグナル

本プロジェクトは、既存製品を置き換えるのではなく、個人専用の投資判断監査・学習システムを目指す。

## 3. スコープ

### 3.1 初期スコープ

- 対象銘柄はまず1銘柄
- 対象領域はハイテク株、半導体、AIインフラ周辺
- 毎朝と引け後にレポートを生成
- 週次で1〜2週間分の総括レポートを生成
- レポートはNotebookLMに渡しやすい形式で出力
- Agentの思考ログを保存
- 簡易的な証拠DBを持つ
- 簡易的な保有中レビューを行う
- 自動売買は行わない

### 3.2 初期スコープ外

初期段階では以下を作らない。

- 自動発注
- 証券API連携
- 本格バックテスト
- 高頻度な場中監視
- 複数銘柄の大規模同時管理
- 完全なポートフォリオ管理
- 本格的なWebアプリケーション
- リアルタイム売買判断

## 4. MVP要件

### 4.1 MVPで作るもの

MVPでは、以下を作る。

- 1銘柄専用の日次レポート
- 朝レポート
- 引け後レポート
- 週次レポート
- 簡易証拠DB
- 強気Agent
- 弱気Agent
- 反証Agent
- 織り込みAgent
- 裁判官Agent
- Agent思考ログ
- NotebookLM投入用テキスト
- localhostで見る管制塔プロトタイプ

### 4.2 MVPの成功条件

MVPの成功条件は利益ではない。

成功条件は以下である。

- 毎日レポートが出る
- レポートが投資判断に使える
- 重要材料の見落としが減る
- 強気だけでなく危険も出る
- ポジションを持つ/持たない理由が整理される
- 週末に反省会ができる
- Agent思考ログから問題箇所を追える
- 1か月継続できる
- サブスク範囲内で運用できる

## 6. Agent要件

### 6.1 探索設計Agent

検索前に、今日確認すべき論点を決める。

役割:

- 中期投資仮説を確認する
- 今日調べるべき情報を定義する
- 仮説を壊す可能性がある論点を出す
- 重要イベント、決算、IR、政策、需給変化をチェック対象にする
- 検索Agentまたは情報収集処理に探索方針を渡す

### 6.2 情報収集

MVPでは検索Agentを細かく分けすぎない。

収集対象:

- 企業IR
- 適時開示
- 決算資料
- 業界ニュース
- 競合ニュース
- 株価、出来高
- 信用、空売り、需給
- SNSや掲示板の過熱感

SNSは売買根拠にしない。過熱感、注目度、噂の発生検知としてだけ扱う。

### 6.3 強気Agent

証拠DBを見て、中期投資仮説を強める材料を整理する。

出力:

- 強気結論
- 根拠となるevidence_id
- 投資仮説への影響
- 強気方向のスコア案
- 不確実性
- 追加確認すべき点

### 6.4 弱気Agent

証拠DBを見て、仮説を弱める材料、ポジションを取るリスク、過熱感を整理する。

出力:

- 弱気結論
- 根拠となるevidence_id
- どの前提が弱まるか
- 弱気方向のスコア案
- 不確実性
- 追加確認すべき点

### 6.5 反証Agent

仮説を壊す可能性のある証拠を探す。

主な問い:

```text
この投資仮説が間違っているなら、何が観測されるはずか？
その兆候は今日の情報に含まれているか？
```

出力:

- 仮説を壊す条件
- 反証候補
- 根拠となるevidence_id
- 反証の強さ
- 判定を変える条件

### 6.6 織り込みAgent

良い材料がすでに株価や需給に反映されていないかを見る。

見るもの:

- 直近の株価上昇率
- 出来高の増加
- 関連銘柄の動き
- ニュース発生後の価格反応
- SNSの過熱感
- 短期勢の流入可能性

出力:

- 織り込み判定
- 過熱判定
- エントリータイミング上の注意
- 根拠となるevidence_id

### 6.7 裁判官Agent

裁判官Agentは、強気、弱気、反証、織り込みの主張を比較し、最終判定を行う。

重要な原則:

- 両論併記だけで中立にしてはいけない
- 強気/弱気の数を比較してはいけない
- 証拠の質、対象銘柄への直接性、数値の明確さ、投資影響度で重み付けする
- 中立は「両論あるから」ではなく、「証拠が拮抗している」または「情報不足で方向判定不能」の場合に限る
- 中立または保留にする場合は、何が確認できれば強気/弱気に傾くかを必ず示す

裁判官Agentの評価軸:

- 証拠忠実性
- 推論妥当性
- 情報源品質
- 数値の明確さ
- 対象銘柄への直接性
- 投資影響度
- 価格への織り込み可能性
- 未確認リスク

裁判官Agentの出力:

- 方向スコア
- 判定
- 確信度
- 証拠重み
- 中立にしなかった理由
- 保留しなかった理由
- まだ危ない点
- 判定が変わる条件

## 7. 方向スコア要件

### 7.1 目的

強気Agentと弱気Agentが必ず両方出ることで、毎回中立に回帰する問題を避ける。

### 7.2 スコア範囲

方向スコアは以下とする。

```text
-100: 強い弱気
0: 中立
+100: 強い強気
```

### 7.3 判定区分

暫定区分:

```text
+70〜+100: 強気
+30〜+69: やや強気
-29〜+29: 中立または保留
-69〜-30: やや弱気
-100〜-70: 弱気
```

### 7.4 中立の定義

悪い中立:

```text
強気意見も弱気意見もあるので中立
```

良い中立:

```text
証拠品質が拮抗している
または
重要論点が未確認で方向判定できない
```

### 7.5 証拠重み

方向スコアとは別に、証拠重みを表示する。

例:

```text
強気: 68%
弱気: 17%
反証: 9%
織込済: 6%
```

重み付け要素:

- 一次情報か
- 数値が明確か
- 対象銘柄への直接性が高いか
- 複数の独立ソースがあるか
- 情報が新しいか
- 投資仮説への影響が大きいか
- 価格にすでに織り込まれていないか

## 8. 証拠DB要件

### 8.1 方針

Agent同士が要約を渡し続ける伝言ゲームにしない。

全Agentは共通の証拠DBを参照し、出力はevidence_idに紐づける。

### 8.2 MVPの証拠DB項目

```text

取得日
発表日時
ソースURL
情報種別
対象銘柄
要点
原文抜粋
数値
信頼度
関連論点
```

### 8.3 将来の証拠DB項目

```text
source_id
URL / 文書名
取得日時
発表日時
原文抜粋
数値
対象企業
対象セクター
情報種別
信頼度
関連論点

```

### 8.4 ソース品質

ソース品質は、できる限りルールまたはスキーマで評価する。

暫定分類:

```text
A: 一次情報、公式資料、明確な数値あり
B: 信頼できる報道、競合情報、業界統計
C: 解釈記事、アナリスト記事、二次情報
D: SNS、掲示板、未確認情報
E: 根拠不足、使用不可
```

## 9. レポート要件

### 9.1 朝レポート

目的:

その日見るべき材料を短時間で把握する。

内容:

```text
1. 今日の市場チェックポイント
2. 昨夜から朝までの重要材料
3. 対象銘柄への影響
4. 中期仮説への影響
5. 今日注意すべきイベント
6. ポジション保有中なら見るべきリスク
```

### 9.2 引け後レポート

目的:

その日の値動きと材料の関係を整理する。

内容:

```text
1. 今日の結論
2. 方向スコア
3. 証拠重み
4. 値動きと出来高
5. 重要ニュース
6. 強気材料
7. 弱気材料
8. 反証リスク
9. 織り込み/過熱感
10. 今ポジションを取るリスク
11. 明日以降に見るべき条件
12. 人間が確認すべき一次情報
```

### 9.3 レポート冒頭の信号表示

毎日読むため、冒頭に短く表示する。

```text
今日の判定: 強気 / やや強気 / 中立 / 保留 / やや弱気 / 弱気
方向スコア: -100〜+100
警戒度: 低 / 中 / 高
今やること: 見るだけ / 追加調査 / ポジション見直し / 撤退検討
```

### 9.4 週次レポート

週次で1〜2週間分の情報をまとめる。

内容:

```text
1. 今週の大きな流れ
2. 中期投資仮説の変化
3. 方向スコアの推移
4. 重要だった材料
5. 見落としそうなリスク
6. 織り込み/過熱感の変化
7. ポジション維持の妥当性
8. 来週見るべき論点
```

## 10. NotebookLM音声化要件

日次レポートと週次レポートは、NotebookLMに投入して音声解説化する。

目的:

- 読む負荷を下げる
- 移動中や作業中に市場動向を聞ける
- 高品質な市場情報を耳でインプットできる
- 投資判断の継続性を上げる

MVPでは、NotebookLMへの完全自動投入までは必須にしない。まずは投入しやすい形式でレポートを生成する。

必要な出力:

- NotebookLM投入用Markdown
- 音声化向け短縮サマリー
- 週次音声レビュー用レポート

## 11. 反省機構要件

### 11.1 目的

レポートを出して終わりにせず、過去判断を振り返り、自分だけの投資判断ログを作る。

### 11.2 反省対象

- その時の考えは妥当だったか
- ポジション管理は正当だったか
- 強気Agentの主張は正しかったか
- 弱気Agentの警告は役に立ったか
- 反証Agentのリスクは現実化したか
- 織り込みAgentの判定は妥当だったか
- 裁判官Agentは中立に逃げていなかったか
- 自分が感情的に判断していなかったか
- 見落とした情報は何か
- 次回から何を改善すべきか

### 11.3 反省レポート形式

```text
1. 期間中の判断一覧
2. 当時の根拠
3. 当時の方向スコア
4. 実際の結果
5. 当たった点
6. 外した点
7. 見落とし
8. Agent別の評価
9. 人間側の判断ミス
10. 次回の改善点
```

## 15. メンテナンス要件

### 15.1 基本方針

メンテ難易度を下げるため、Agentロジック、データ保存、表示を分離する。

### 15.2 実装方針

- データはJSON、Markdown、CSVなど単純な形式で保存する
- 画面は保存済みデータを読むだけにする
- Agentロジックと表示ロジックを分ける
- 各Agentの出力形式を固定する
- エラーも画面に出す
- 手動再実行ボタンを用意する
- 設定は1つのconfigファイルに集約する
- NotebookLM用出力をボタンでコピーできるようにする

### 15.3 Agent出力JSON例


### 15.4 壊れた時に分かるようにすること

- どのAgentが失敗したか
- どの情報取得が失敗したか
- 証拠DBが更新されたか
- Agent出力がスキーマに合っているか
- レポート生成が完了したか
- NotebookLM用出力が生成されたか

## 16. 将来の自動売買要件

自動売買は最後のおまけである。

もし将来追加する場合は、以下を必須とする。

### 16.1 前提条件

- 十分な判断ログがある
- 反省機構が機能している
- ペーパートレードで有効性が確認されている
- 安全ゲートがある
- 人間が即停止できる

### 16.2 安全条件

- 小額運用
- 発注回数制限
- 最大損失制限
- キルスイッチ
- 人間承認
- 出金権限なし
- 読み取りAPIキーと発注APIキーを分離
- 手動解除なしでは再開しない

### 16.3 将来必要な機能

- バックテスト
- ペーパートレード
- 注文管理
- 約定管理
- 部分約定対応
- 注文失敗時の処理

- データ異常検知
- API障害時停止
